# 杭州 ECS 视频提音与 Demucs 性能测试

结论：当前 2 vCPU、约 1.83 GiB RAM 的 ECS 可承接已验证的视频提音试用场景；不建议启用默认 `htdemucs_ft` 的日常分轨服务。模型能加载，但固定资源测试处理 30 秒音频，在 900 秒内没有完成，已由 systemd 超时终止。没有取得完整分轨结果，不能报告成功吞吐或推算完整歌曲的完成时间。

测试日期：2026-11-19（北京时间）。实例 `i-bp1dhypbynl7gfsclml5`，杭州。
系统 Alibaba Cloud Linux 3；CPU 报告为 Intel Xeon Platinum；RAM 1870 MiB，Swap 约 4095 MiB。

## 已部署服务

- 私有 H5：`127.0.0.1:8782`。
- 独立提音 API：`127.0.0.1:8783`，`ordinary-muse-api.service`。
- 提音限额：512 MiB RAM、100% CPU quota，串行队列；不导入或加载 PyTorch。
- 支持 M4A、WAV、AIFF、CAF，试听、下载、任务持久化、完成后保留 24 小时。
- Demucs 已安装在独立模型环境，四份官方缓存权重的 SHA-256 均核对通过。未启用常驻分轨 API；界面明确展示分轨暂未启用。
- 原乐谱 H5 和反馈服务继续正常运行。没有开放 80/443 或其他新公网监听，也未修改安全组。

## 视频提音实测

输入为以此前测试歌曲的前 30 秒音频合成的 64×64 MP4，旨在验证音轨解码、导出和接口。此测试不代表所有高码率视频、容器或并发规模的表现。

| 导出格式 | 无模型负载的处理耗时 | 模型诊断轮运行时的处理耗时 |
| --- | ---: | ---: |
| M4A | 2.15 s | 3.95 s |
| WAV | 1.26 s | 2.90 s |
| AIFF | 1.24 s | 1.90 s |
| CAF | 1.26 s | 1.87 s |

以上为服务端处理时间，不含网络上传。四种格式的下载、M4A 预览分段请求和完成后整整 24 小时的到期时间均通过检查。初次测试后提音服务 cgroup 峰值约 84.85 MiB。共存测试发生在第一轮诊断期间，与固定限额模型基准分别记录。

## Demucs 固定限额基准

- 模型：`htdemucs_ft`（项目默认的四模型组合）。
- Python 3.11.13，Torch/Torchaudio 2.1.0+cpu，Demucs 4.0.1，NumPy 1.26.4。
- 输入：歌曲前 30 秒，44.1 kHz、双声道 WAV；调用项目现有 `separator.py`，没有更换轻量模型或缩短模型内部配置。
- CPU quota 150%（最多约 1.5 vCPU）、Torch 2 线程、Nice 10；内存上限固定 1600 MiB；运行时限 900 秒。
- 约 11:11:53 启动，约 11:26:53 超时。模型加载成功，未生成最终四轨文件。

| 指标 | 实测 |
| --- | ---: |
| 最终结果 | `timeout`，SIGTERM 15，非 OOM 退出 |
| 墙钟时限 | 900 s，未完成 |
| CPU 累计时间 | 526.31 s |
| cgroup RAM 峰值 | 1,225,601,024 bytes，约 1168.82 MiB / 1.14 GiB |
| cgroup RAM + Swap 峰值 | 1,925,378,048 bytes，约 1.79 GiB |
| 5 秒采样的进程组 Swap 峰值 | 1,330,683,904 bytes，约 1.24 GiB |
| 采样的主机 Swap 使用峰值 | 1,410,016 KiB，约 1.34 GiB |
| 内存限额命中次数 | 0 |

RAM 峰值包括 cgroup 计入的内存，并非应用堆大小；RAM 与 Swap 的各自峰值不一定发生在同一时刻，不能直接相加。CPU 累计时间不等于实际等待时间。未完成的 900 秒测试只能说明耗时下界，不能当作成功任务耗时。

第一轮采用 1300 MiB 保护限额，触及限额并产生大量换页；中途放宽后又主动终止。该轮标为 `aborted_diagnostic`，不作为固定限额性能基准。第二轮从头以 1600 MiB 运行，未命中该限额，仍有明显换页并最终超时。诊断时 `vmstat` 观察到较高 I/O 等待，不应将所有延迟仅归因于 CPU。
